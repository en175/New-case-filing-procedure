# AI模拟被申请人 Bot 开发 PRD

## 一、需求背景

### 1.1 功能目标

在在线立案流程中增加“AI模拟被申请人”能力，让申请人在提交案件前，提前体验被申请人可能提出的抗辩意见。

该能力用于帮助申请人识别自己主张中可能存在的合同依据、履行事实、证据材料、金额计算和责任范围问题，从而更理性地理解后续仲裁或调解过程。

### 1.2 上线范围

1. 页面使用前端固定写死的 6 张通用抗辩卡片。
2. 用户点击卡片后，进入被申请人口吻对话。
3. 每轮对话调用模型生成回复。
4. 支持用户上传 PDF 文件，并调用现有 OCR 能力抽取文本，作为对话辅助上下文。
5. 模型异常、超时或输出非法时，前端使用本地兜底话术。
6. 用户与 Bot 完成至少 3 轮有效交互后，允许继续下一步。
7. 所有对话回复、开场白和兜底话术必须直接使用被申请人口吻，不得出现“模拟”“被申请人口吻”“AI将”“系统将”“下面将”等元说明或旁白说明。

### 1.3 不做范围

1. 不做动态卡片生成。
2. 不支持非 PDF 文件上传。
3. 不做多文件管理、文件夹管理、证据目录自动生成。
4. 不做 OCR 结果人工校对流程。
5. 不做案件胜败判断。
6. 不预测仲裁庭观点。
7. 不代表广州仲裁委员会、仲裁庭或仲裁员发表实体意见。
8. 不根据模型自行生成具体调解金额、退款金额、赔偿金额或分期金额。
9. 不引导申请人补做、伪造、篡改、删除证据。
10. 不做长篇法律意见书。
11. 不输出任何元说明或旁白说明。

## 二、页面流程

### 2.1 主流程

1. 用户进入“AI模拟被申请人”页面。
2. 页面展示 6 张固定抗辩卡片。
3. 用户选择一个抗辩场景。
4. 页面收起卡片区，并展示已选择的抗辩卡片。
5. 系统使用该卡片的 `opening_message` 发出首轮被申请人口吻开场。
6. 用户可输入追问或反驳内容，也可上传 1 个 PDF 文件作为补充材料。
7. 用户上传 PDF 后，系统调用 OCR 能力抽取文本，并将 OCR 摘要作为后续对话辅助上下文。
8. 后端携带案件概要、所选卡片、历史对话、用户本轮输入和 PDF OCR 上下文调用模型。
9. 前端展示模型返回的 `reply`。
10. 用户完成至少 3 轮有效交互后，“继续下一步”按钮可用。
11. 用户点击继续后，进入后续立案确认流程。

### 2.2 交互轮次定义

1. 用户发送 1 次有效文本，且系统完成 1 次回复，计为 1 轮。
2. 点击卡片后的 `opening_message` 不计入轮次。
3. 用户只输入空白、无意义符号、重复粘贴同一句，不计入轮次。
4. 完成至少 3 轮有效交互后，继续下一步按钮可用。

## 四、模型调用接口

### 4.1 PDF 上传与 OCR

上线版本按最小可用范围实现：

1. 仅支持 PDF 文件。
2. 建议先限制单次会话最多上传 1 个 PDF。
3. 上传入口放在对话输入区附近，不放到卡片选择区。
4. 用户上传 PDF 后，前端展示文件名和识别状态。
5. OCR 识别成功后，后端生成 `ocr_text_digest`，作为后续模型调用上下文。
6. OCR 识别失败时，不阻断对话，前端提示“文件暂未识别成功，您仍可继续文字沟通。”
7. OCR 文本只作为辅助材料，不替代申请书、案件概要或用户本轮输入。
8. 模型不得把 OCR 内容表述为已经核验的原件事实。
9. OCR 相关对话回复和兜底话术不得出现“模拟”“被申请人口吻”“AI将”“系统将”“下面将”等元说明或旁白说明。

建议文件限制：

| 项目 | 建议规则 |
|---|---|
| 文件类型 | 仅允许 `.pdf` |
| 文件数量 | 单次会话 1 个 |
| 文件大小 | 建议不超过 20MB |
| OCR 文本长度 | 建议传入摘要或截断文本，不把超长全文直接塞入模型 |

非 PDF 文件处理：

```text
当前仅支持上传 PDF 文件。请重新选择 PDF 材料，或直接用文字说明相关内容。
```

### 4.2 入参

每轮调用对话模型时，后端至少传入以下字段：

```json
{
  "case_summary": {
    "dispute_type": "合同纠纷",
    "claimant_claims": [
      "请求被申请人返还服务费",
      "请求被申请人承担仲裁费用"
    ],
    "core_dispute": "申请人主张被申请人未按约履行服务义务，被申请人可能围绕履行情况、证据充分性和金额计算提出抗辩"
  },
  "selected_defense_card": {},
  "uploaded_pdf_context": {
    "file_name": "合同材料.pdf",
    "ocr_status": "success",
    "ocr_text_digest": "OCR 识别出的材料要点或截断文本",
    "ocr_warning": "OCR 结果可能存在识别误差，仅作为辅助上下文"
  },
  "conversation_history": [],
  "latest_user_message": "用户本轮最新输入",
  "round_count": 1,
  "negotiation_offer_scope": null
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `case_summary` | object | 是 | 案件概要，由申请书、事实说明或材料识别结果整理而来。 |
| `selected_defense_card` | object | 是 | 用户选择的抗辩卡片，直接使用前端固定卡片对象。 |
| `uploaded_pdf_context` | object/null | 是 | 用户上传 PDF 的 OCR 上下文。未上传或识别失败时传 `null`。 |
| `conversation_history` | array | 是 | 当前卡片下的历史对话。建议只传最近 8-12 轮，避免上下文过长。 |
| `latest_user_message` | string | 是 | 用户本轮最新输入。 |
| `round_count` | number | 是 | 当前有效交互轮次。点击卡片后的开场白不计入轮次。 |
| `negotiation_offer_scope` | object/null | 是 | 可协商金额或履行范围。没有明确后端配置时必须传 `null`。 |

### 4.3 出参

模型每轮只输出以下 JSON：

```json
{
  "reply": "我方不认可你方这个说法。你方需要先说明，该项请求具体依据哪一份合同、哪一条约定以及哪一份材料？",
  "risk_flag": "normal",
  "should_end": false
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `reply` | string | 是 | 前端实际展示的被申请人口吻回复，80-120 字为宜，不输出 Markdown、不输出表格。 |
| `risk_flag` | string | 是 | 风险标记，默认 `normal`。 |
| `should_end` | boolean | 是 | 默认 `false`。0604 上线版本建议只记录日志，不做强中断。 |

### 4.4 risk_flag 枚举

| risk_flag | 场景 | 前端处理 |
|---|---|---|
| `normal` | 正常抗辩对话 | 展示 `reply`。 |
| `evidence_misconduct` | 用户要求补做、伪造、修改、删除证据 | 展示 `reply`，不额外弹窗。 |
| `adjudication_request` | 用户要求判断胜败、胜诉概率、仲裁庭是否支持 | 展示 `reply`，引导回事实、证据和合同依据。 |
| `institution_impersonation` | 用户要求代表广州仲裁委员会、仲裁庭或仲裁员表态 | 展示 `reply`，强调不能代表机构。 |
| `unsafe_or_irrelevant` | 辱骂、无关、恶意测试或明显偏离当前争议点 | 展示 `reply`，拉回当前抗辩场景。 |

### 4.5 金额限制

当 `negotiation_offer_scope` 为 `null` 时，模型不得自行生成具体退款金额、赔偿金额、付款金额、分期金额或调解金额。

只有后端明确传入可协商范围时，模型才可以在该范围内表达沟通空间。

## 五、前端状态流转

| 状态 | 触发条件 | 页面表现 | 下一步 |
|---|---|---|---|
| `card_selecting` | 用户进入页面 | 展示 6 张固定抗辩卡片；输入框不可用或提示先选场景。 | 用户点击卡片。 |
| `opening` | 用户点击卡片 | 卡片区收起；展示已选卡片；系统发送 `opening_message`。 | 进入对话。 |
| `chatting` | 首轮开场完成 | 输入框可用；用户可继续追问或反驳。 | 每轮调用对话模型。 |
| `ocr_processing` | 用户上传 PDF 后 | 展示文件名和“识别中”；输入框可继续使用或短暂禁用。 | OCR 成功或失败。 |
| `thinking` | 用户发送消息后 | 输入框禁用；展示回复中状态。 | 等待模型返回。 |
| `fallback_reply` | 模型失败、超时或输出非法 | 用本地兜底话术回复。 | 回到 `chatting`。 |
| `ready_to_continue` | 用户与 Bot 完成至少 3 轮有效交互 | “继续下一步”按钮可用。 | 跳转下一流程。 |

## 六、异常兜底

### 6.1 单次失败兜底

模型异常、超时或输出非法时，前端不得展示“模型调用失败”“AI服务异常”等研发话术。前端应根据已选卡片展示本地兜底回复：

```text
我方仍然坚持该抗辩意见。你方需要进一步说明对应的合同依据、事实依据和证据材料，否则我方不会认可你方的全部请求。请你方先明确：你方主张的责任具体对应哪一份材料？
```

### 6.2 多次失败兜底

如果同一会话连续多次失败，前端展示：

```text
当前仍可继续围绕该争议点沟通。请你方先补充合同依据、履行经过、证据材料或金额计算方式，我方会基于你方补充内容继续回应。
```

### 6.3 输出非法处理

以下情况视为输出非法，前端应丢弃模型结果并使用兜底回复：

1. 不是合法 JSON。
2. 缺少 `reply`、`risk_flag` 或 `should_end`。
3. `reply` 为空。
4. `reply` 出现代表广州仲裁委员会、仲裁庭或仲裁员作出判断的内容。
5. `reply` 引导用户伪造、补做、篡改、删除证据。
6. `reply` 在没有 `negotiation_offer_scope` 的情况下自行承诺具体金额。

## 七、验收标准

### 7.1 功能验收

1. 页面初始展示 6 张固定抗辩卡片。
2. 用户点击卡片后，卡片区收起，并展示已选卡片。
3. 系统使用所选卡片的 `opening_message` 作为首轮开场。
4. 开场白不计入有效交互轮次。
5. 页面支持上传 PDF 文件，且拒绝非 PDF 文件。
6. PDF OCR 成功后，后续模型调用包含 `uploaded_pdf_context`。
7. OCR 失败不阻断用户继续文字对话。
8. 用户完成至少 3 轮有效交互后，继续下一步按钮可用。
9. 模型失败时，页面展示正式业务兜底话术，不展示研发异常信息。
10. 模型回复、开场白和兜底话术不得包含“模拟”“被申请人口吻”“AI将”“系统将”“下面将”等元说明或旁白说明。

### 7.2 模型验收

1. 模型始终使用被申请人口吻。
2. 模型不输出法律咨询式中立分析。
3. 模型每轮只围绕一个核心问题回应。
4. 模型回复不判断胜败，不预测仲裁庭观点。
5. 模型不代表广州仲裁委员会、仲裁庭或仲裁员表态。
6. 模型不引导补做、伪造、篡改、删除证据。
7. 模型不在没有 `negotiation_offer_scope` 的情况下生成具体金额。
8. 模型可以参考 PDF OCR 内容追问，但不得声称 OCR 内容已经被核验为真实原件。
9. 模型回复不得出现任何元说明或旁白说明。

### 7.3 文案验收

1. 页面可见文案使用中文业务系统表达。
2. 不出现“AI仅供参考”“未接真实后端”“模型调用失败”等内部演示或研发说明。
3. 不出现英文 UI 文案。
4. 不出现表情符号。
5. 不出现遮挡、重叠或影响阅读的问题。

### 7.4 开发交付验收

1. 前端卡片数据可直接复制本文件第三节 JSON。
2. PDF 上传和 OCR 规则可直接参考本文件第四节。
3. 后端调用参数可直接参考本文件第四节。
4. 状态流转和异常兜底可直接参考本文件第五至六节。
5. 模型 Prompt 以 `AI模拟被申请人bot开发提示词.md` 为准。
